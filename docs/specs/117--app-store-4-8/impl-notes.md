## Implementation Notes

### Task 1

- 採用方針: Passkey API の request / response DTO と `PasskeyRepository` protocol / real implementation を Core 境界に追加し、View / ViewModel から network や credential raw data を直接扱わない前提を作った。
- 重要な判断: `options.publicKey` wrapper は必須 decode とし、欠落時は decode failure に倒す。`registration/finish` は `{user_id}` のみを decode し、`authentication/begin` request は `{code_challenge}` のみを送るテストで未知 field 混入を防いだ。
- 重要な判断: サーバ側 #216 は 2026-07-24 時点で GitHub Issue は open だが `staged-for-release` label 付きで、repo 運用上は develop merge 済みを示すため task 1 の依存は満たすものとして実装した。
- 残存課題: 次 task では coordinator 側で base64url string を AuthenticationServices の `Data` に変換する。Task 1 では repository DTO 上の base64url 文字列保持までを対象にした。

### Task 2

- 採用方針: AuthenticationServices 依存を `PasskeyPlatformAuthorizationCoordinator` に閉じ、server WebAuthn options から platform request を作って WebAuthn-compatible credential envelope へ戻す境界を追加した。
- 重要な判断: `challenge` / `user.id` / credential descriptor ID のみ base64url decode し、`rp.id` / `rpId` は provider に渡す relying party domain string として扱う。`excludeCredentials` は decode して保持するが、iOS 16 minimum では platform request へ適用できないため degraded best-effort として明示した。
- 重要な判断: Coordinator と performer は `@MainActor` に隔離し、active attempt が controller / continuation bridge を強参照する。cancel は `ASAuthorizationController.cancel()` へ伝播し、continuation は exactly-once resume して release する。
- 残存課題: 次 task では LoginViewModel 側から本 coordinator を注入し、PKCE / repository / token exchange と接続する。Account sheet からの passkey add flow は task 5 scope。

### Task 3

- 採用方針: `LoginViewModel` に Google / passkey login / passkey registration 共通の attempt state machine を追加し、passkey ceremony は repository / coordinator / existing auth exchange 境界へ接続した。
- 重要な判断: signup は `registration/finish` の `{user_id}` を token handoff に使わず、platform registration envelope の `rawId` を local allowed credential として assertion request にだけ渡す。`authentication/begin` request は引き続き `{code_challenge}` のみを送る。
- 重要な判断: finish dispatch 前の cancellation は `.canceled`、registration/authentication finish dispatch 後の cancellation / timeout / decode failure は `.resultUnknown` に分けた。token exchange dispatch 後は cancellation で止めず、exchange success なら `onAuthenticated` まで進める。
- 重要な判断: Reviewer round 1 の指摘を受け、`LoginView.swift` の passkey-aware UI 差分は task 3 range から除外した。既存 UI 互換の `LoginViewState` は旧 shape に戻し、passkey 固有の attempt kind / resultUnknown は `LoginViewModel.attemptStatus` に分離した。
- 残存課題: Login UI の passkey button / signup form / dismissal wiring は task 4 scope。AppEnvironment production injection は task 6 scope。

### Task 5

- 採用方針: Account sheet の passkey add flow を `AccountViewModel` の `PasskeyEnrollmentState` と injectable `PasskeyRepository` / `PasskeyPlatformAuthorizationCoordinating` に閉じ、View は add task の所有と dismissal cancellation だけを担当する構成にした。
- 重要な判断: add finish dispatch 前の cancellation は `.canceled`、finish dispatch 後の cancellation / decode failure は `.resultUnknown` に分け、どの失敗でも `state` の loaded user と current authenticated session を維持する。
- 重要な判断: add / logout / 退会は共同 guard と presentation 値型で制御し、add 中は logout/delete を disabled、logout/delete confirmation 中は add を開始しない。退会 action は非表示にせず既存 delete flow の success/failure state を維持した。
- 残存課題: `AccountRouteView` への production passkey dependency wiring は task 6 scope のため、Task 5 時点では default unavailable dependency のまま任意注入可能に留めた。
